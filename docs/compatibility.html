Что происходит на старом браузере

Браузер, не знающий @layer, пропускает не одно правило, а весь блок целиком — то есть всю библиотеку. Слои несут и собранные файлы, и правила, которые JS-рантайм создаёт для data-gr-layout: рантайм отработает без ошибок, вставит <style>, и браузер его проигнорирует.

Страница остаётся читаемой, но не оформленной. Текст, ссылки, поля и кнопки на месте и работают: разметка семантическая, контент не спрятан за скриптом. Но не будет ни сеток, ни компонентов, ни отступов, ни тем — документ выглядит как HTML без CSS. Ошибки в консоли при этом нет: игнорирование неизвестного правила — штатное поведение CSS, и отлаживать здесь нечего.

Ниже порога :has() или контейнерных запросов картина другая и куда мягче: не применяется та часть правил, что их использует. Без :has() поле не подсветит отключённое состояние, без контейнерных запросов утилиты с суффиксом -c* не сработают — остальное оформление остаётся на месте.

Постоянной зависимости у проекта нет, пакет тянется разово через npx; без сети скрипт падает с объяснением, а не печатает устаревшее. Сборки -scoped: порог выше

Файлы griffincss-ui-scoped.css и griffincss-utils-scoped.css обёрнуты в @scope (.griffin) — они нужны тем, кто подмешивает библиотеку в чужую вёрстку и хочет ограничить её областью. Порог у них принципиально другой: Firefox 146 — это осень 2025 года, и мировая доля падает с 95,3 % до 90,0 %, а измеримая российская — с 96,8 % до 83,8 %.

Одним предложением на все файлы это не описывается, поэтому строка отдельная: обычные сборки порога @scope не требуют, и выбор -scoped — это осознанная плата за изоляцию. Что именно теряет scoped-сборка помимо порога, разобрано в разделе «Стратегии оформления».

Проверить у себя

Библиотека не везёт ни баннера, ни детекта: это решение приложения, а не CSS-пакета. Если баннер нужен вам — вот весь код. Наличие CSSLayerBlockRule проверяется объектной моделью, потому что CSS.supports отвечает про свойства и селекторы, а не про at-правила: 

var ok = typeof CSSLayerBlockRule !== 'undefined'          // каскадные слои
      && CSS.supports('selector(:has(*))')                 // :has()
      && CSS.supports('container-type: inline-size');      // контейнерные запросы

document.documentElement.dataset.grSupported = ok ? 'yes' : 'no';

Третья строка ставит атрибут на <html> — дальше баннер показывается обычным CSS-правилом [data-gr-supported="no"] .my-banner { display: block }. Проверять @scope отдельно имеет смысл только тем, кто подключил -scoped-файлы: CSS.supports('selector(:scope)') для этого не годится и ответит true где угодно — здесь работает typeof CSSScopeRule !== 'undefined'.

Чего не будет

ПросьбаОтвет
Сборка без каскадных слоёв Нет. Это не снятие обёрток @layer, а пересмотр специфичности всей библиотеки: слои позволяют утилите с одним классом побеждать компонент с двумя. Без них порядок ломается — прецедент известен по .gr-hidden против .gr-flex-md. Второй артефакт со своим прогоном тестов ради нескольких процентов трафика на браузерах, где нет и :has(), библиотека не потянет.
Развилки @supports под каждую возможность Нет. Запасная ветка на каждую возможность удвоила бы вывод, который получают все, ради сред, которых у целевой аудитории нет.
Полифилы и запасные раскладки Нет. Порог назван и измерен; проект, которому нужны браузеры ниже него, эта библиотека не обслуживает — и лучше знать это до подключения, чем после.
