# Потоковая раскладка гридов во время парсинга HTML

Дата: 2026-08-23. Статус: согласовано, к реализации.

## Задача

Сейчас рантайм ждёт `DOMContentLoaded` и раскладывает все контейнеры одним
проходом. До этого момента каждый контейнер с `data-gr-layout` держится
FOUC-защитой на `opacity: 0`. На длинной или медленно приходящей странице это
значит: весь размеченный контент невидим, пока не придёт последний байт HTML.

При этом раскладка контейнера известна раньше — атрибут `data-gr-layout`
приходит вместе с открывающим тегом, то есть в тот момент, когда парсер только
создал элемент и ещё не наполнил его детьми. Ждать конца документа незачем.

**Цель:** контейнер получает свою сетку и открывается сразу после того, как
парсер его создал, а не после `DOMContentLoaded`. Страница проявляется сверху
вниз по мере загрузки, как обычный HTML.

## Что меняется для пользователя библиотеки

Ничего в разметке и ничего в публичном API. Тот же тег `<script>` в `<head>`
начинает раскладывать гриды по мере их появления. Аварийный выключатель —
`data-stream="false"` на теге скрипта — возвращает прежнее поведение.

Потоковый режим требует синхронного скрипта в `<head>`. С `defer` или скриптом
в конце `<body>` парсинг уже завершён, и режим сам собой вырождается в нынешний
`init()` — отдельной обработки этот случай не требует.

## Механизм

`MutationObserver` с `childList: true, subtree: true` на `document.documentElement`,
поднятый синхронно при загрузке скрипта, если `document.readyState === 'loading'`.
Браузер отдаёт мутации микротаском после каждой порции парсинга; узел приходит
в колбэк с уже разобранными атрибутами, но, как правило, ещё без детей.

Отвергнутые альтернативы:

- **опрос по `requestAnimationFrame`** — запаздывание на кадр (те самые 16 мс,
  ради которых всё затевается) и полное сканирование документа каждый кадр,
  то есть O(n) на кадр при растущем n. Хуже всего работает ровно на длинных
  страницах, ради которых задача и ставится;
- **опережающий разбор текста ответа** (Service Worker или серверная
  интеграция) — вне архитектуры «один тег `<script>`, и всё работает».

## Решения по спорным местам

### Авто-присвоение `gr-area-*` — инкрементально, с починкой конфликта

Нынешний `assignAreaClasses` требует видеть всех детей разом: собирает занятые
имена, затем раздаёт свободные по порядку. При потоковой обработке дети
приходят по одному, и заранее неизвестно, займёт ли следующий ребёнок явным
классом имя, которое мы уже кому-то выдали.

Правило: ребёнок без класса получает первое имя, не занятое явно и не выданное
ранее — немедленно. Ребёнок с явным `gr-area-X`, где `X` уже выдан рантаймом
другому ребёнку, отбирает имя: прежний владелец получает следующее свободное,
и если оно тоже отобрано — каскад продолжается.

**Инвариант:** после полной загрузки контейнера результат совпадает с тем,
что дал бы нынешний пакетный алгоритм на том же контейнере. Это и есть главный
тест раздачи областей.

### FOUC-защита остаётся как есть

Правила не меняются: `opacity: 0` до `.gr-ready`, `opacity: 1` с
`transition: opacity 0.3s ease` после. В потоковом режиме контейнеры получают
`.gr-ready` поштучно, поэтому проявление идёт сверху вниз по мере загрузки —
это и есть желаемый эффект. `opacity: 0` при этом продолжает страховать от
вспышки неразложенного контента, если браузер успеет отрисовать кадр между
вставкой узла и колбэком.

**Проверено в браузере (2026-08-23):** в потоковом режиме плавное появление
не проигрывается вовсе — ноль событий `transitionstart` против четырёх на той
же странице с `data-stream="false"`. Причина в устройстве браузера: колбэк
наблюдателя выполняется микротаском в той же задаче, что и вставка узла,
поэтому контейнер ни разу не рисуется прозрачным. Решение принято: оставить
как есть. Контейнер появляется сразу разложенным, а `opacity: 0` остаётся
страховкой на случай, когда браузер всё же успел отрисовать кадр.

Отдельно проверена гипотеза, почему эффект не виден на `docs/slow.html`:
там `data-auto="false"`, поэтому защита не ставится при загрузке скрипта,
а внутри `init()` вставка правила `opacity: 0` и простановка `.gr-ready`
происходят синхронно в одном кадре — состояние «прозрачно» браузер ни разу
не отрисовывает, и переходу не от чего стартовать. Проверка подтвердила:
событий перехода ноль. Правка не требуется — на страницу добавлено пояснение.

### Брейкпоинты читаются раньше — и сверяются позже

Потоковый режим читает `--gr-bp-*` в момент загрузки скрипта. Синхронный скрипт
дожидается выполнения предшествующих таблиц стилей, поэтому при обычном порядке
тегов (`<link>` выше `<script>`) значения верные. Но если `griffincss-grid.css`
подключён после скрипта, в медиазапросы уйдут фолбэки из `BREAKPOINTS`.

Страховка: на `DOMContentLoaded` `init()` перечитывает токены и сравнивает
отпечаток значений с прежним. Разошлись — таблица пересобирается целиком
(кеши сброшены, классы раскладок сняты, документ пройден заново). Обычный
порядок тегов при этом не платит ничего: отпечаток совпадает, пересборки нет.

### Демонстрация — свой стрим-сервер

Статический файл приходит целиком за миллисекунды, потоковую раскладку на нём
не увидеть. Нужен сервер, отдающий HTML порциями с паузами.

## Архитектура

### Точки входа и жизненный цикл

`autoStart` разветвляется как сейчас, но первая ветка меняется:

| `readyState` | Было | Стало |
|---|---|---|
| `loading` | ждать `DOMContentLoaded` → `init()` | поднять наблюдателя парсинга; на `DOMContentLoaded` — `init()` как финальная сверка |
| иначе | `init()` | `init()` |

`init()` идемпотентен: уже обработанные контейнеры лежат в `touched`, их набор
раскладок уже в `generatedSets`, повторный проход только сверяет. Финальная
сверка нужна для узлов, которых наблюдатель не увидел, — например вставленных
скриптом в разметке до его старта.

`destroy()` гасит наблюдателя парсинга наравне с наблюдателями из `observe()`.

Публичный API не расширяется: `init`, `refresh`, `observe`, `destroy`,
`parseLayout`, `version`. Потоковый режим — поведение автостарта, а не новая ручка.

### Инкрементальная обработка узла

Тело цикла из `processLayouts` выносится в `processElement(el)`; `processLayouts`
становится обёрткой над `querySelectorAll` + `processElement`. Обе точки входа
идут через одну функцию, поэтому расхождению поведения взяться неоткуда.

На каждый добавленный узел `N` в родителе `P` наблюдатель парсинга делает:

1. есть layout-атрибут у `N` → `processElement(N)`;
2. `N` пришёл поддеревом (вставка через `innerHTML`) → проход по потомкам;
3. `P` — уже разложенный контейнер → `N` получает область по правилам выше.

CSS флашится один раз на колбэк, а не на элемент: `flushCSS` переписывает
`textContent` целиком, и вызов на каждый элемент дал бы квадратичную стоимость
по объёму CSS.

### Состояние

Запись в `touched` расширяется указателем на следующее свободное имя области —
без него инкрементальная раздача на каждого ребёнка пересчитывала бы занятые
имена заново. `destroy()` сбрасывает его вместе с остальным состоянием.

### Сохраняемые инварианты

Все инварианты рантайма из [CONTRIBUTING.md](../../CONTRIBUTING.md) остаются в силе. Текст, порядок и
медиадиапазоны генерируемых правил не меняются — значит компайл-тайм-миксин
`packages/grid/scss/_layout-mixins.scss` не трогается и `generate.test.js`
продолжает сравнивать два одинаковых вывода. Меняется только момент выдачи.

## Демонстрация

- `scripts/serve-stream.mjs` — сервер на `node:http` без зависимостей: отдаёт
  `docs/` как статику, а `docs/stream.html` режет на порции по маркеру-комментарию
  и отправляет с паузой между ними;
- `npm run demo:stream` — запуск;
- `docs/stream.html` — страница с контейнерами, приходящими сверху вниз, и
  ссылкой на себя же с `data-stream="false"` для сравнения «как было раньше»;
- `docs/slow.html` по существу не меняется: она про медленный JS, это другой
  сценарий.

## Проверка

Юнит-тесты в `packages/grid/test/runtime.test.js` (мок DOM умеет подавать
мутации вручную через `MockMutationObserver.instances`):

1. контейнер получает класс раскладки, будучи добавленным без детей;
2. ребёнок получает `gr-area-*` сразу при добавлении в разложенный контейнер;
3. явный `gr-area-X` у позднего ребёнка отбирает имя, прежний владелец
   переназначается;
4. поток и пакет дают одинаковый итог на одном и том же контейнере;
5. `data-stream="false"` возвращает прежний путь;
6. `destroy()` снимает наблюдателя парсинга;
7. CSS флашится один раз на колбэк, а не на элемент.

Живая проверка в браузере на стрим-сервере: раскладка приходит по мере
загрузки, консоль чистая, поведение при `data-stream="false"` — прежнее.

## Вне рамок

- оптимизация `flushCSS` до точечной вставки правил через CSSOM — нынешняя
  перезапись `textContent` раз на порцию парсинга приемлема; если профиль
  покажет обратное, это отдельная задача;
- потоковая обработка утилитных классов — они чистый CSS и в рантайме
  не нуждаются;
- интеграция со Service Worker или серверный рендер классов.
