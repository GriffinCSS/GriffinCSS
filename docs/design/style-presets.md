# Стратегии оформления: четыре стиля одним атрибутом

Дата: 2026-08-25. Статус: согласовано, к реализации. Этап 10 плана работ.

## Задача

Фреймворк должен уметь менять настроение оформления целиком — установкой
одной переменной, без правки разметки и без второй сборки. Стилей четыре:

| Стиль | Настроение |
|---|---|
| `standard` | как сейчас: скруглённые границы, цветные кнопки, ориентир — стандартные темы Bootstrap |
| `airy` | легче и воздушнее: скругления крупнее стандартных, цвета пастельнее, анимации оживлённее |
| `strict` | строгий: скруглений нет или они малы, строгие кнопки и заголовки, границы и дивидеры бледнее, фоны светлее — ближе к белому на светлой теме, графитовые на тёмной |
| `compact` | компактный журнальный: близок к строгому, отступы меньше, скругления по минимуму, но есть. Упор на максимум информации с чёткой разбивкой по блокам |

## Решение: третья ось, устроенная как две существующие

В проекте уже есть две ортогональные оси оформления, и обе сделаны одинаково:
атрибут на любом элементе, значения — в миксинах `_theme-values.scss`, правила —
в `_theme.scss`, переключатель — в `griffincss-theme.js`.

```html
<html data-gr-theme="dark" data-gr-style="strict" data-gr-a11y="low-vision">
```

Стиль становится третьей осью того же устройства. Значения атрибута:
`standard` (равносильно отсутствию атрибута), `airy`, `strict`, `compact`.
Любая из 4×3×2 комбинаций обязана работать — это условие приёмки, а не пожелание.

Селекторы пишутся парой:

```scss
:root[data-gr-style="airy"],
[data-gr-style="airy"] { … }
```

Первый — специфичность (0,2,0) — выигрывает у блока `:root` внутри своего
слоя. Второй обслуживает островки: `<section data-gr-style="compact">`
внутри воздушной страницы.

### Новый слой каскада

Специфичности мало. `griffincss-ui.scss` и `griffincss-utils.scss` подключают
`griffincss-core/scss/tokens` **внутрь собственных слоёв** — это сделано
намеренно, чтобы собранный файл каждого пакета был самодостаточным. Значит
`:root` существует в трёх слоях сразу, вплоть до `griffincss.utils`, а слой
перебивает любую специфичность. Файл стилей в слое `griffincss.core` молча
проиграл бы базовым токенам на любой странице с `griffincss-ui.css`.

Поэтому порядок слоёв дополняется пятым, последним:

```css
@layer griffincss.reset, griffincss.core, griffincss.ui, griffincss.utils, griffincss.style;
```

Пользовательский CSS вне слоёв по-прежнему выигрывает у библиотеки без
`!important` — принцип не нарушается, слои проигрывают беслойным правилам
целиком.

Эта строка — константа, повторённая в шести точках входа, в
`scripts/check-dist.mjs` и в JS-рантайме, который печатает её в свой
`<style>`. Все копии сверяются между собой, поэтому правятся одной ревизией.

**В слой `griffincss.style` уходят только токены.** Структурные правила
компонентов остаются в `griffincss.ui`: подними их в последний слой, и
`[data-gr-style="compact"] .gr-table` начал бы выигрывать у `.gr-mb-0`,
сломав правило «утилиты старше компонентов».

## Поставка: opt-in файл, ядро не растёт

`standard` — это нынешнее оформление, оно уже в `griffincss-core.css` и
никакого блока не требует. Три остальных стиля живут в отдельном
`packages/core/dist/griffincss-styles.css`. Кто его не подключил — не платит
ни байта, и бюджет ядра (≤ 5 КБ gzip на CSS+JS) не трогается.

Точка входа — `packages/core/scss/griffincss-styles.scss`. В `dist` лежит один
собранный файл со всеми тремя стилями. Поштучные артефакты
(`griffincss-style-airy.css` и подобные) не выпускаются: выигрыш для страницы
измеряется сотнями байт, а цена — четыре сборочные команды, четыре артефакта
в `check-dist.mjs` и четырёхкратное дублирование общей части.

Кому нужен ровно один стиль, собирает из SCSS — тем же способом, каким уже
настраиваются брейкпоинты.

## Конфигурация: один список на оба пакета

```scss
// Один раз, до любой точки входа
@use 'griffincss-core/scss/style-config' with ($gr-styles: (strict, compact));

@use 'griffincss-core/scss/griffincss-styles';
@use 'griffincss-ui';
```

`packages/core/scss/_style-config.scss` объявляет `$gr-styles: (airy, strict,
compact) !default` и проверяет список: неизвестное имя — `@error`, как парсер
раскладки ругается на невалидный ввод. Пустой список `()` — ни одного стиля
и ни одного правила оси в компонентах.

Точка конфигурации одна на оба пакета: `griffincss-ui` peer-зависит от ядра и
читает список оттуда (`@use 'griffincss-core/scss/style-config' as cfg`) — так
же, как уже берёт `$gr-breakpoints`. Двум спискам разойтись негде.

`standard` в список не входит: в ядре ему нечего объявлять, а в компонентах
стандартное оформление и есть базовое правило модуля.

## Ручки: чем стиль управляет

Ось управляет токенами, а не правилами. Пять ручек уже есть, три вводятся.

| Ручка | Статус | Роль |
|---|---|---|
| `--gr-radius` | есть | скругление. Каскад скруглений из `griffincss-utils` подхватывает новое значение сам |
| `--gr-border-width` | есть | толщина линий |
| `--gr-transition` | есть | длительность **и** кривая: «оживлённее» — это `cubic-bezier`, а не только время |
| `--gr-leading-base`, `--gr-tracking-base` | есть | плотность текста |
| `--gr-radius-pill` | **новый** | `999px` захардкожен в ~20 местах `griffincss-ui` (бейджи, прогресс, аватар, спиннер). Без токена строгий стиль оставит таблетки таблетками |
| `--gr-density` | **новый** | множитель компонентной плотности |
| `--gr-elevation` | **новый** | множитель плотности теней |

### Почему плотность — множитель, а не прямое значение

`--gr-gap` в `_tokens.scss` имеет адаптивный шаг: с брейкпоинта `md` значения
крупнее. Переопредели стиль `--gr-gap` напрямую — он бы этот шаг снёс. Поэтому
базовые значения переписываются на `calc(… * var(--gr-density))`, а стиль
двигает один множитель:

```scss
--gr-gap: calc(0.75rem * var(--gr-density));
```

Множитель применяется к `--gr-gap`, `--gr-gap-sm`, `--gr-gap-lg`, `--gr-ui-gap`,
`--gr-control-height`, `--gr-control-height-sm`, `--gr-control-height-lg` и
`--gr-control-padding-x`.

**Утилиты отступов ось не трогает.** `.gr-p-4` живёт на собственной шкале
`$gr-spacing-base: 0.25rem` и от `--gr-gap` не зависит. Это не упущение:
утилита — явное указание автора страницы, и стилю не место в нём.

### Почему высота теней — отдельный множитель

`--gr-shadow-strength` задаёт тема (1 в светлой, 2.6 в тёмной — иначе тень на
тёмном фоне не видна). Стилю нужно ослабить тени независимо от темы, а
`--gr-shadow-strength: calc(var(--gr-shadow-strength) * 0.5)` — циклическая
ссылка, CSS её запрещает. Отсюда второй множитель: тени считаются как
`calc(5% * var(--gr-shadow-strength) * var(--gr-elevation))`.

## Цвета: сдвиг относительно темы, а не абсолютные значения

Механика ровно та, что уже работает в `gr-a11y-contrast`. Стиль не знает,
какая тема действует; он перенаправляет триплет на **якорь**, а значение
якоря задаёт тема:

```scss
// в блоке стиля
--gr-hsl-border: var(--gr-hsl-border-soft);
```

Благодаря этому блок стиля пишется один раз и работает поверх обеих тем.

Якоря объявляются **не в ядре**, а в `griffincss-styles.css` — тем же набором
из четырёх селекторов, что и в `_theme.scss`:

```scss
:root, [data-gr-theme="light"]   { @include sv.gr-style-anchors-light; }
[data-gr-theme="dark"]           { @include sv.gr-style-anchors-dark; }
@media (prefers-color-scheme: dark) {
  :root:not([data-gr-theme]), [data-gr-theme="auto"] { @include sv.gr-style-anchors-dark; }
}
```

Якорь — обычная наследуемая переменная, поэтому светлый островок внутри
тёмной секции переобъявит якоря и стиль на нём посчитается от светлых значений.

Якоря принадлежат стилям, а не всем сразу, поэтому попадают в файл только
вместе со своим стилем — это и есть основная экономия от `$gr-styles`.

| Якорь | Чей | Смысл |
|---|---|---|
| `--gr-hsl-accent-soft`, `--gr-hsl-accent-soft-hover` | airy | пастельный акцент: ниже насыщенность, светлее в светлой теме |
| `--gr-hsl-on-accent-soft` | airy | чернила на пастельной заливке. Без него `primary`-кнопка получила бы белый текст на пастели и провалила контраст |
| `--gr-hsl-surface-0-tinted`, `-1-tinted`, `-2-tinted`, `-sunken-tinted`, `-overlay-tinted` | airy | все пять ступеней поверхности в одном оттенке |
| `--gr-hsl-border-tinted`, `--gr-hsl-border-strong-tinted` | airy | линии в том же оттенке, что поверхности |
| `--gr-hsl-border-soft`, `--gr-hsl-border-strong-soft` | strict, compact | бледные границы и дивидеры |
| `--gr-hsl-surface-0-lifted`, `--gr-hsl-surface-1-lifted`, `--gr-hsl-surface-2-lifted`, `--gr-hsl-surface-sunken-lifted` | strict, compact | фоны к краю шкалы: к белому в светлой теме, к графиту в тёмной |

`--gr-hsl-border-strong-soft` существует отдельно от `--gr-hsl-border-soft`
намеренно. Написать `--gr-hsl-border-strong: var(--gr-hsl-border)` внутри блока
стиля можно, но `var()` подставит **уже сдвинутое** значение, и сильная линия
растворится вместе со слабой.

**Статусы: стиль трогает заливку, но не текстовый цвет.**

Первая редакция запрещала оси касаться статусов вовсе — «пастельная опасность
это сигнал, потерявший силу сигнала». Правка по итогам просмотра: запрет был
слишком широким. Сигнал теряется, когда бледнеет *текст* статуса на белом
фоне; заливка кнопки может быть какой угодно светлоты, если чернила на ней
подобраны под неё.

Отсюда у каждого из четырёх статусов три роли вместо одной: цвет текста
(`--gr-hsl-status-danger`), цвет заливки (`--gr-hsl-status-danger-surface`)
и чернила на заливке (`--gr-hsl-on-status-danger`). Раньше такая пара была
только у предупреждения; остальные три брали заливку из текстового токена,
а чернила — из общего `--gr-color-on-accent`. Эта асимметрия и сломалась,
как только воздушный стиль перекрасил акцент: чернила акцента уехали
на зелёную и красную кнопки.

Стиль меняет заливку и чернила, текстовый цвет не трогает. Строгий не трогает
статусы вовсе — строгость это геометрия и линии.

Два исключения, обнаруженные при просмотре и оставленные сознательно:

- **Красная кнопка воздушного стиля остаётся со светлой подписью.** Белый
  текст на красном — устоявшийся знак отказа, и единообразие с соседями
  не стоит его потери. Заливка ради этого держится темнее прочих: на
  светло-красном белый даёт 3,9:1, на выбранном — 5,1:1.
- **Жёлтая заливка журнального стиля приглушается в светлую сторону**, а не
  в тёмную вместе с остальными. Потемневший жёлтый читается как оливковый,
  а «внимание» держится на узнаваемости оттенка, а не на насыщенности.

**Подмес в линии считается отдельно от подмеса в поверхности.** Нейтрально-серая
граница вокруг подкрашенного фона читается как рассогласование, поэтому линии
воздушного стиля берут тот же оттенок. Но не ту же насыщенность: воспринимаемая
цветность примерно пропорциональна `S × (1 − |2L − 1|)`, и при светлоте 82 %
одна и та же цифра видна втрое сильнее, чем при 97 %, а при 52 % — в шестнадцать
раз. Механическая подстановка сделала бы тему синей вместо нейтральной, поэтому
насыщенность у линий ниже: 14 % у обычной и 6 % у сильной против 22–25 %
у поверхностей. Итоговая цветность держится в пределах 2,5× от фоновой —
это условие приёмки, проверяемое тестом.

**Подкрашиваются все ступени, а не выборочные.** Оставленная нейтральной
ступень возвращает ровно тот дефект, ради которого подмес и делался: серая
деталь посреди подкрашенных соседей. Сначала так вышло у линий, потом
у утопленной поверхности, потом у всплывающей — меню оставалось белым листом
над подкрашенной страницей. Теперь полнота проверяется тестом: каждая из пяти
ступеней и обе линии обязаны ссылаться на подкрашенный якорь.

Два ограничения, вытекающие из физики цвета:

- **Фон страницы в светлой теме остаётся чистым белым.** Подмешать оттенок
  в белый можно только потемнив его, то есть отказавшись от белого листа.
  В тёмной теме такого ограничения нет, и там фон подкрашен.
- **Порядок ступеней важнее силы подмеса.** В светлой теме это
  overlay → surface-1 → sunken → surface-2, в тёмной — зеркально, причём
  утопленная уходит **под** фон страницы. Первая редакция дала ей в тёмной
  теме ту же светлоту, что у фона, и она перестала быть утопленной; тест
  на порядок ступеней в обеих темах появился именно после этого.

Relative color syntax (`hsl(from … h calc(s * .6) l)`) отвергнут: он позволил
бы обойтись без якорей, но утяжелил бы каждый из 28 цветов ядра и лишил бы
возможности выверить контраст вручную для конкретной пары «стиль × тема».

## Три ловушки наследования и общая часть файла

`var()` в значении custom property подставляется на том элементе, где свойство
**объявлено**; вниз наследуется уже готовое значение. Это уже описано в
`_theme.scss` применительно к цветам, и ось стиля наступает на те же грабли
трижды. Элемент с `data-gr-style`, но без `data-gr-theme`, переопределил бы
ручку и унаследовал бы результат предка — то есть не изменился бы вовсе.

Поэтому файл стилей несёт **общую часть**, повторяющую на `[data-gr-style]`
три блока ядра:

1. `gr-semantic-colors` — резолв `--gr-color-*` из триплетов;
2. метрики плотности — всё, что считается через `var(--gr-density)`, включая
   повтор внутри `@media (width >= md)`;
3. набор `--gr-shadow-*` — из-за `var(--gr-shadow-strength)` и `var(--gr-elevation)`.

Чтобы значения не разъехались, блоки 2 и 3 выносятся из `_tokens.scss` в
миксины (`gr-density-metrics`, `gr-shadow-set`) — так же, как в своё время
`gr-semantic-colors` был вынесен в `_theme-values.scss`. `_tokens.scss` их
подключает, файл стилей подключает те же.

Побочный эффект блока 3: тёмный островок внутри светлой страницы сейчас
получает тени светлой темы (`--gr-shadow-*` объявлены единственный раз в
`:root`). При подключённом файле стилей и стилем на островке этот дефект
исчезает. **В ядре он в рамках этапа не чинится** — это отдельное изменение
поведения существующего кода, ему место в отдельном шаге, а не внутри новой
возможности. Зафиксирован в рисках.

В общую часть входит и блок `[data-gr-style="standard"]`, возвращающий ручки к
базовым значениям: `standard` — валидное значение атрибута, и стандартный
островок внутри воздушной страницы обязан работать даже тогда, когда собран
один-единственный стиль.

## Приоритет осей

Тема → стиль → доступность, причём режим для слабовидящих перебивает первые два.

Само по себе это не выйдет: блоки a11y лежат в ядре, файл стилей подключается
позже, специфичность одинаковая — победил бы стиль. Поэтому файл стилей несёт
короткий блок отмены с более высокой специфичностью:

```scss
[data-gr-a11y="low-vision"][data-gr-style],
[data-gr-a11y="low-vision"] [data-gr-style] { … }
```

Он возвращает контраст **целиком** — тем же миксином `gr-a11y-contrast`, что
действует в ядре, а не отдельным набором значений. Иначе получалось так:
строгий стиль уводит `--gr-hsl-border` к бледному якорю, слой оси старше слоя
ядра, и режим для слабовидящих оставался с линиями стиля — то есть ровно без
того, ради чего его включали. Стиль вправе двигать цвет, пока его об этом
не просили иначе; просьба «сделай контрастно» старше любого оформления.

Плотность возвращает единице только журнальный стиль — единственный, кто
ужимает интерфейс; воздушный своего простора не теряет, «крупнее
и просторнее» режиму доступности не противоречит. Написать общее
`--gr-density: max(1, var(--gr-density))` нельзя: свойство сослалось бы само
на себя, а цикл CSS обнуляет целиком, и плотность пропала бы вовсе.

Отмена привязана к явному `data-gr-a11y="low-vision"` и не повторяется под
`prefers-contrast` — по той же причине, по которой в `_theme.scss` типографика
режима включается только явным выбором: системное «больше контраста»
не означает «увеличь шрифт».

## Пресеты

Ориентиры. Точные значения выверяются в браузере на шаге визуальной проверки.

| | `--gr-radius` / `--gr-radius-pill` | `--gr-density` | `--gr-transition` | `--gr-elevation` | цвет |
|---|---|---|---|---|---|
| `standard` | 0.5rem / 999px | 1 | 0.2s ease | 1 | без сдвигов |
| `airy` | 1rem / 999px | 1.15 | 0.28s cubic-bezier(0.34, 1.56, 0.64, 1) | 0.9 | акцент, ссылки и заливки статусов на пастельные якоря, поверхности мягче |
| `strict` | 0.125rem / 0.25rem | 1 | 0.12s ease-out | 0.4 | линии на `-soft`, поверхности на `-lifted`, статусы не трогаются |
| `compact` | 0.1875rem / 0.25rem | 0.75 | 0.1s ease-out | 0.3 | поверхности от `strict`, но линии и цвета свои: линии заметнее базовых, цвета приглушены |

`compact` дополнительно опускает `--gr-leading-base` до 1.3 и уменьшает кегль
страницы до 93.75 % — процентом, а не в rem: процент считается от кегля,
который выбрал пользователь в настройках браузера, поэтому стиль складывается
с этой настройкой, а не отменяет её. Вся шкала задана в rem, поэтому вместе
с кеглем пропорционально сжимаются отступы, высоты контролов и радиусы;
`--gr-control-font-size` при этом остаётся `1rem` — уменьшать его отдельно
значило бы умножить дважды.

Линии `compact` — его главное отличие от `strict`, а не плотность: строгий
уводит границы в фон, журнальный делает их заметнее базовых. Полоса
в журнальной вёрстке рабочий инструмент разбивки, и стиль без видимых линий
превращается в строгий с мелким шрифтом.

Кривая воздушного стиля даёт лёгкий overshoot — это и есть «анимации чуть
более оживлённые». `prefers-reduced-motion` уже обслуживается существующими
модулями и осью не затрагивается.

## Структурные правила в griffincss-ui

`check-dist.mjs` проверяет попарно (`core↔ui`, `core↔utils`, `ui↔utils`), что ни
один класс не встречается в двух пакетах. Значит правило вида
`[data-gr-style="strict"] .gr-btn` не может лежать в файле ядра — оно уезжает
в пакет компонентов.

**Но и в модуль компонента оно лечь не может.** Правило проекта
([CONTRIBUTING.md](../../CONTRIBUTING.md), «Extra rules for `packages/ui/`
components») запрещает модулям селекторы
по `[data-gr-theme]` и `[data-gr-a11y]`, и по той же причине запрещает
`[data-gr-style]`: в scoped-сборке селектор получает префикс `:where(.griffin)`,
то есть требует носитель атрибута **внутри** области, а он стоит на
`<html>`. В `griffincss-ui-scoped.css` такие правила были бы мёртвым грузом —
собираются, проходят все проверки, молча не работают.

Поэтому структурные правила живут в отдельном модуле
`packages/ui/scss/_style-rules.scss`, который подключает только обычная точка
входа. В проекте это третий случай того же приёма: `@keyframes` подключаются
вне области, потому что имя анимации ищется глобально, а тема — потому что
`data-gr-theme` стоит на `<html>`.

**Следствие: scoped-сборка получает ось только на уровне токенов.** Скругления,
плотность, тени, цвета в ней работают полностью — токены глобальны и лежат вне
области. Структурных отличий (шапка карточки линией, плотная таблица) в ней
нет. Ограничение документируется рядом с двумя уже существующими.

- **strict** — `.gr-card-header` теряет подложку и остаётся линией;
  `.gr-btn` без тени, вес 500; `.gr-table th` плотнее по трекингу.
- **compact** — `.gr-table` с плотными ячейками и видимыми разделителями строк
  по умолчанию; пояса карточки уже; `.gr-alert` и `.gr-menu` компактнее.
- **airy** — `.gr-card` с тенью вместо границы; заметнее отклик `:active` у кнопки.

Оценка: 30–50 селекторов, около 2 % к `griffincss-ui.css`. При `$gr-styles: ()`
рост нулевой. `griffincss-ui-scoped.css` не растёт вовсе.

`check-dist.mjs` получает проверку, сторожащую это устройство: в
`griffincss-ui-scoped.css` не должно быть ни одного вхождения `[data-gr-style`.
Без неё правило, добавленное в модуль по невнимательности, вернётся тем самым
молчаливым дефектом.

**Заголовки `h1`…`h6` ось не трогает.** Они живут в опциональном ресете, и
правило для них сработало бы не у всех. «Строгие заголовки» реализуются только
на компонентных — шапка карточки, заголовок модалки, шапка таблицы; для текста
страницы есть классы типографики.

## Рантайм

`packages/core/src/griffincss-theme.js` получает третью ось по образцу двух
существующих:

- `Griffincss.theme.style(value)` — установка; `standard` снимает атрибут,
  неизвестное значение приводится к `standard`;
- ключ `gr-style` в `localStorage`, с тем же молчаливым откатом при недоступном
  хранилище;
- поле `style` в `state()` и в событии `griffincss:themechange`.

Файл собирается копированием из `src/` в `dist/`, как и сейчас.

## Риски

1. **Забытая ловушка наследования.** Пропусти общая часть один из трёх блоков —
   островок молча не изменится, а на `<html>` всё будет работать, потому что
   `:root` и `[data-gr-style]` там один элемент. Ловится только тестом на
   островке; он в списке обязательных.
2. **Неполная правка порядка слоёв.** Строка `@layer griffincss.reset, …`
   существует в восьми местах и сверяется `check-dist.mjs` — в том числе с
   константой `LAYER_ORDER` внутри `griffincss.js`. Пропущенная копия роняет
   проверку, а не приводит к тихому дефекту, поэтому риск управляемый. Само
   же старшинство слоя проверяется на витрине с намеренно переставленными
   тегами `<link>`.
3. **Тени в островке темы.** Дефект существует и сейчас; ось его чинит только
   там, где стоит `data-gr-style`. Асимметрия сознательная, отдельным шагом
   после этапа.
4. **Бюджет `griffincss-ui`.** Пакет при цели ≤ 10 КБ gzip растёт на 30–50
   селекторов. Замер обязателен; при превышении правила `airy` (самые
   декоративные) первыми уходят из состава по умолчанию.
5. **Комбинаторика проверки.** 4 стиля × 3 состояния темы × 2 состояния
   доступности = 24 сочетания. Автотест проверяет механику (какой блок
   выигрывает), а не внешний вид; глазами смотрятся 8 сочетаний стиля и темы
   плюс два крайних с доступностью.
6. **`--gr-density` и утилиты.** Ожидание «компактный стиль ужмёт и `.gr-p-6`»
   не оправдается. Это устройство, а не дефект, но его надо назвать в
   документации явно, иначе оно вернётся баг-репортом.
